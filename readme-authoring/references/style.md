# README style rules

**Read when**: writing or refining the prose of a README.

Use normal source-project documentation language:

- Prefer short declarative sentences.
- Use the names that appear in the repository.
- Explain technical terms once, then use them consistently.
- Use numbered lists for ordered work and bullets for component lists.
- Keep directory trees short and annotate only useful entries.
- Use code blocks for commands, paths, and configuration snippets.
- Keep glossary definitions brief and specific.

Avoid:

- Process commentary about the author, model, prompt, or drafting
  process.
- Marketing language, generic assurances, and broad claims.
- Unexplained internal review mechanics in a reader-facing overview.
- Placeholder values, unavailable runtime metadata, and speculative
  examples.
- Artificial contrast phrasing such as "X, not Y" when a direct
  statement is clearer.
- Jargon-heavy headings when plain headings work better.

Examples of clearer wording:

| Avoid | Prefer |
|---|---|
| "What this work produces" | "Overview of deliverables" |
| "The specifications are developed contract-first" | "Start by defining the shared contracts" |
| "immutable run plan" | "test execution plan" |
| "environment block" | "test environment" |
| "implementation cohort" | "comparable implementation attempts" |
